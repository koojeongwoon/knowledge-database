# Python 장기 실행 서비스 메모리 가이드

이 문서는 메모리 증가를 줄이고 원인을 측정하기 위한 기준입니다. 캐시가 유지하는 참조,
일시적인 최대 메모리 사용량, 객체 오버헤드, 해제 후 allocator가 보유하는 메모리를 구분합니다.
RSS가 즉시 감소하지 않는 것만으로 누수를 판정하지 않습니다.

## 1. 캐시와 락의 상한 및 수명

- 사용자별 캐시는 항목 수와 제거 정책을 명시합니다. `StorageManager`는 최근 접근 순서를
  갱신하는 LRU 캐시로 최대 32개 참조를 보유하며, 조회·등록·제거를 짧은 전역 스레드 락으로 보호합니다.
  클라이언트 생성은 전역 락 밖에서 실행하고 고정 64개 생성 락으로 같은 사용자의 중복 생성을 방지합니다.
  생성 락이 겹친 사용자의 캐시 미스·무효화는 대기할 수 있지만 캐시 적중은 이 락을 사용하지 않습니다.
  무효화는 진행 중인 생성이 완료된 뒤 참조를 제거합니다. 다음 조회도 설정 fingerprint를 다시 비교합니다.
  병렬 생성되는 S3 매니저는 각각 별도 Boto3 Session을 사용합니다.
- 캐시 항목 수는 프로세스 전체의 살아 있는 인스턴스 수와 다릅니다. 제거된 매니저도 실행 중인
  호출자가 참조할 수 있습니다. 캐시 제거 시 공유 클라이언트를 즉시 `close()`하지 않습니다.
  명시적 자원 종료가 필요하면 마지막 사용자가 끝난 시점을 소유권 계약으로 관리합니다.
- OAuth 세션 락은 `ServerSessionStore`별 고정 256개를 사용하고 세션 해시를 같은 락으로 매핑합니다.
  보유자와 대기자가 같은 객체를 계속 사용하도록 `revoke()`에서도 락을 제거하지 않습니다.
  서로 다른 세션이 같은 락에 매핑될 수 있어 갱신 시 추가 대기가 발생할 수 있습니다.
  유효한 액세스 토큰의 조회는 락 없이 반환하며, 다중 프로세스 갱신은 기존 Redis 락으로 보호합니다.
- 세션 조회는 Redis 오류와 실제 키 부재를 구분해야 합니다. 일반 캐시의 오류 은닉 경로를
  세션 만료 판정에 사용하지 않습니다. 일시적인 저장소·인증서버 장애는 503을 반환하고
  쿠키를 보존합니다. 실제 만료·폐기는 401 또는 로그인 리다이렉트와 쿠키 제거로 처리합니다.
- `asyncio.Lock.locked()`가 `False`여도 깨어나기를 기다리는 사용자가 있을 수 있습니다.
  이를 근거로 세션별 락을 제거하지 않습니다.
- `functools.lru_cache`의 기본 상한은 128개입니다. 프로젝트에서 크기를 명확히 표현하려면
  `maxsize`를 명시하고, 사용자 입력이 키가 되는 장기 실행 경로에서 `maxsize=None`을 피합니다.
- TTL만으로 높은 입력률에서의 메모리 상한이 보장되지는 않습니다. 외부 Redis 캐시도
  항목 수, TTL, 메모리 정책을 별도로 관리합니다.

## 2. DB 결과 버퍼와 소비 측 적재

Psycopg의 일반 `conn.cursor()`는 결과 전체를 클라이언트 메모리에 보관합니다.
일반 커서의 `for row in cur`와 `fetchmany()`는 Python 객체의 동시 생성을 줄이지만,
드라이버의 전체 결과 버퍼를 제거하지 않습니다.

대량 읽기에서는 `PostgresDatabaseManager.streaming_cursor()`를 사용합니다.
이 메서드는 명시적 트랜잭션 안에서 이름 있는 서버 커서를 열고 `itersize=500`으로 순회합니다.
정상 종료, 예외, 제너레이터의 명시적 종료 시 커서 → 트랜잭션 → 연결 순서로 자원을 반환합니다.
연결은 순회가 끝날 때까지 점유되므로 순회 중 외부 API 호출이나 느린 작업을 피합니다.
다른 DB 어댑터의 기본 `streaming_cursor()`는 일반 커서 호환 경로이며 별도 구현이 필요합니다.

```python
with db.streaming_cursor(batch_size=500) as cur:
    cur.execute("SELECT file_path, content_hash FROM knowledge_documents WHERE owner_id = %s", (owner_id,))
    for file_path, content_hash in cur:
        process(file_path, content_hash)
```

- `iter_document_chunks()`는 행마다 청크를 변환합니다. 인덱싱 소비자는 이를 직접 순회해
  기존 임베딩 맵을 만들며 중간 청크 리스트를 유지하지 않습니다.
- 제너레이터를 중간에 멈추는 호출자는 `contextlib.closing()` 또는 `try/finally`의 `close()`로
  커서와 연결을 반환해야 합니다. 제너레이터 자체를 장기 보관하지 않습니다.
- 기존 `get_document_chunks()`는 호환성을 위해 전체 리스트를 반환합니다.
  `get_all_file_hashes()`와 `get_file_hashes()`도 전체 딕셔너리를 반환합니다.
  이 결과와 소비 측 임베딩 맵의 메모리는 여전히 데이터 크기에 비례합니다.
  전체 처리 메모리의 상한이 필요하면 계획 수립과 임베딩 소비 계약까지 배치 단위로 변경해야 합니다.

## 3. 도메인 객체의 `slots=True`

대량 생성되고 필드가 고정된 데이터클래스에 `slots=True`를 적용합니다.
현재 청크 계획, 인벤토리, 문서 메타데이터, 실행 결과, 이벤트, 온톨로지 및 커밋 모델에 적용되어 있습니다.
Python 3.10 이상에서 지원합니다.

이는 인스턴스 `__dict__` 오버헤드를 줄입니다. 문자열, 임베딩 배열, 내부 컨테이너의 크기나
생존 기간은 줄이지 않습니다. 절감률은 실제 데이터와 객체 수를 포함해 측정합니다.
적용 전에는 `__dict__`/`vars()`, 동적 속성, 상속, weak reference, 직렬화 경로를 확인합니다.
다른 모델에 일괄 확대하기 전에 해당 사용 경로를 검증합니다.

## 4. 문자열과 비동기 작업

- 큰 문자열·바이너리를 반복 조합할 때 `join`, `StringIO`, `BytesIO` 또는 출력 스트림을 검토합니다.
  `join`을 위해 전체 입력을 리스트로 보관하면 입력과 출력이 동시에 존재하므로 최대 메모리를 측정합니다.
  결과 전체가 필요하지 않으면 파일·네트워크에 배치로 씁니다.
- 백그라운드 작업의 소유자, 취소, 예외 처리, 동시 실행 수를 정합니다.
  Python 3.11 이상에서는 `TaskGroup`을 사용할 수 있습니다.
- 작업 집합을 유지한다면 완료 콜백에서 참조를 제거하고 예외도 회수합니다.
  대기 작업·큐의 개수에는 상한이나 backpressure를 둡니다. 완료 콜백만으로 유입량을 제한할 수는 없습니다.

## 5. GC와 OS 메모리 반환

`gc.collect()`는 도달 가능한 캐시나 살아 있는 작업의 참조를 제거하지 않습니다.
GNU libc의 `malloc_trim(0)`은 반환 가능한 빈 메모리의 OS 반환을 시도하며 반환을 보장하지 않습니다.
플랫폼과 allocator에 의존하므로 필수 배치 후처리로 사용하지 않습니다.
도입할 경우 실제 Linux 런타임에서 RSS 효과, 실행 시간, 반복 할당 비용을 측정한 뒤 선택합니다.

## 6. 검증 및 완료 기준

1. 동일 프로세스에서 준비 부하 후 동일 작업을 반복합니다. 사용자 수, 문서 수·크기,
   청크 수, 병렬도, 오류·취소 비율을 고정해 결과를 비교합니다.
2. 각 반복의 최대 RSS와 종료 후 RSS, `tracemalloc`의 현재·최대 할당량,
   캐시 항목 수, 미완료 작업 수, 열린 연결·파일 수를 기록합니다.
   `tracemalloc`에는 드라이버·네이티브 버퍼 전체가 포함되지 않으므로 RSS도 함께 봅니다.
3. 락은 대기자 깨우기·취소·세션 폐기·다수 세션 유입 후에도 같은 세션의 상호 배제를 유지하고
   256개로 고정되어야 합니다. 스토리지 캐시는 다중 스레드 접근 후 32개 이하여야 합니다.
4. DB 검증은 500개를 넘는 결과의 순서·owner 분리·빈 결과와 정상·오류·중도 종료의 연결 반환을 확인합니다.
5. 반복 종료 후 살아 있는 객체·자원이 계속 증가하지 않고 일정 범위에서 안정화되는지 판단합니다.
   로컬 회귀 테스트 통과와 운영 환경의 장시간 안정성 검증은 별도로 기록합니다.

```sh
.venv/bin/python -m pytest -q tests/test_oauth_session.py tests/test_settings_web.py tests/test_storage_cache.py tests/test_memory_streaming.py
```

실제 PostgreSQL 검증은 격리된 테스트 DB 주소를 `KNOWLEDGE_MEMORY_TEST_DATABASE_URL`로 지정합니다.
미지정 시 해당 통합 테스트 3개는 건너뜁니다. 테스트 데이터는 연결별 임시 테이블에만 생성됩니다.

### 2026-09-29 로컬 검증 기록

- 전체 회귀 테스트: 감사 로그의 외부 DB 저장만 대체한 실행에서 325개 통과, 9개 건너뜀.
  최초 일반 실행의 감사 로그 파일 테스트 1개는 DB 연결 대기로 실패했고 단독 재실행은 통과했습니다.
- 격리된 PostgreSQL 16 통합 검증: 커서 수명 단위 테스트와 함께 7개 통과.
  1,200개 청크의 다중 배치, 순서·벡터 변환, owner 분리, 중도 종료·쿼리 오류의 연결 반환을 확인했습니다.
- 6회 반복에서 회당 새 사용자 키 2,000개를 처리한 뒤 락 256개, 캐시 32개가 유지되었습니다.
  스토리지 생성은 테스트 대역이고 청크 조회는 실제 PostgreSQL을 사용했습니다.
  준비 반복 후 `tracemalloc` 현재 할당량은 약 8,841~8,848 KiB였으며 운영 RSS 검증은 수행하지 않았습니다.
- 실제 S3 클라이언트·장시간 운영 부하의 메모리 추이는 별도 측정 대상입니다.
  감사 로그의 무제한 큐는 이후 단계에서 별도 파일 큐와 용량 제한 outbox로 변경했습니다.
  포화·재시도·운영 볼륨 조건은 [감사 로그 운영 가이드](AUDIT_LOGGING.md)를 참고합니다.

후속 단절 방지 검증:

- 세션 오류 분류와 생성 락 축소 후 전체 회귀 테스트는 감사 DB 저장을 격리한 상태에서
  338개 통과, 9개 건너뜀입니다. 변경 경로 테스트 83개도 통과했습니다.
- Redis 장애와 실제 키 부재, 만료 토큰 갱신 장애 후 복구, 페이지 쿠키 유지 및 복구,
  두 API 인증 경로의 503/401 구분, 콜백 장애의 503 응답을 확인했습니다.
- 같은 생성 락에 매핑된 사용자라도 캐시 적중은 느린 생성 작업을 기다리지 않는지,
  서로 다른 생성 락의 병렬 생성, 생성 중 무효화, 생성 실패 후 재시도를 검증했습니다.
- 실제 Boto3 클라이언트 4개를 동시에 생성하고 Stubber로 각 매니저의 bucket 요청을 확인했습니다.
  이 검증은 외부 S3 네트워크 요청을 발생시키지 않았으며 실제 장애·지연 부하 시험은 별도입니다.
